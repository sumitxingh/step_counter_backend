Step Counter API

REST reference for the mobile app and the internal admin dashboard. Mirrors the running implementation — see docs/design.md for rationale and docs/postman/ for a runnable collection.

Base URL
http://localhost:3000
Auth
Bearer <access_token>
Casing
snake_case everywhere
Content-Type
application/json
Token TTL
7 days · no refresh
Errors
{ status_code, message, error }

Conventions

Applies to every endpoint unless noted otherwise.

  • Every route except the four under /auth/* requires Authorization: Bearer <access_token>.
  • All fields are snake_case — request bodies, responses, query params, everywhere. No camelCase.
  • Unknown fields are silently dropped, not rejected. A typo'd field name won't 400 — it just won't be saved. Check names against this doc if a change isn't taking effect.
  • password_hash is never returned on any user object.
  • Timestamps (created_at, updated_at, last_login_at) are ISO 8601. entry_date is a plain YYYY-MM-DD date, no time component.
  • Pagination / window params (page, limit, days) are query strings, not body fields. All optional with per-endpoint defaults.

Error shape

Every non-2xx response uses this shape.

{
  "status_code": 400,
  "message": "Invalid credentials",
  "error": "BAD_REQUEST"
}

Validation errors (400) return message as an array of strings, one per failed rule — e.g. ["email must be an email", "password must be longer than or equal to 8 characters"]. Every other error returns message as a single string.

StatuserrorWhen
400BAD_REQUESTRequest body failed validation
401UNAUTHORIZEDMissing / invalid / expired token, or wrong login credentials
403FORBIDDENValid token but insufficient role (non-admin on /admin/*), or is_active = false at login
404NOT_FOUNDResource doesn't exist
409CONFLICTe.g. registering an email already in use

Auth

No token required. full_name / email / password are required unless marked optional.

POST/auth/register No auth

Create an account. Returns an access token and the new user. password must be ≥ 8 characters.

Request

{
  "full_name": "Jane Doe",
  "email": "jane@example.com",
  "password": "password123"
}

Response 201

{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "user": {
    "id": "39d76e58-4557-45e8-8e54-fd6d1535e384",
    "full_name": "Jane Doe",
    "email": "jane@example.com",
    "age": null,
    "gender": null,
    "height_cm": null,
    "weight_kg": null,
    "daily_goal_steps": 8000,
    "role": "user",
    "is_active": true,
    "last_login_at": null,
    "created_at": "2026-08-21T16:12:25.796Z",
    "updated_at": "2026-08-21T16:12:25.796Z"
  }
}

Errors

  • 400 invalid payload
  • 409 email already registered

Store access_token in secure storage (e.g. flutter_secure_storage) and send it as Authorization: Bearer <token> on every later request. Expires in 7 days — there is no refresh flow, re-login when it expires.

POST/auth/login No auth

Exchange credentials for a token. Response is the same shape as Register. last_login_at is stamped on every successful login.

Request

{
  "email": "jane@example.com",
  "password": "password123"
}

Response 201

{ "access_token": "eyJ...", "user": { /* same shape as Register */ } }

Errors

  • 401 wrong email or password — same error for both, doesn't reveal which
  • 403 account disabled (is_active = false)
POST/auth/forgot-password No auth

Request a password-reset token by email.

Request

{ "email": "jane@example.com" }

Response 201

{ "message": "If that email exists, a reset link has been sent" }

Always the same response, whether or not the email exists, to avoid leaking which emails are registered. If it exists, a reset token is emailed and expires after RESET_TOKEN_TTL_MIN (30 min in local dev). The client can't check token status — the UI should just say “check your email”.

POST/auth/reset-password No auth

Set a new password using the token from the reset email. new_password must be ≥ 8 characters.

Request

{
  "token": "the-token-from-the-email",
  "new_password": "newpassword123"
}

Response 201

{ "message": "Password reset successful" }

Errors

  • 401 token invalid, expired, or already used

Users

All require a bearer token. There is no :id param — these always act on the logged-in user, derived from the token.

GET/users/me User

Full profile of the current user. Same object as the user in Register / Login, without the wrapping keys.

Response 200

{
  "id": "39d76e58-4557-45e8-8e54-fd6d1535e384",
  "full_name": "Jane Doe",
  "email": "jane@example.com",
  "age": 28,
  "gender": "female",
  "height_cm": 165,
  "weight_kg": 60,
  "daily_goal_steps": 8000,
  "role": "user",
  "is_active": true,
  "last_login_at": "2026-08-21T16:13:57.321Z",
  "created_at": "2026-08-21T16:12:25.796Z",
  "updated_at": "2026-08-21T16:13:57.323Z"
}
PATCH/users/me User

Update profile fields. All optional — send only what changed.

Request

{
  "age": 28,
  "gender": "female",
  "height_cm": 165,
  "weight_kg": 60
}

gender is free-text — the API doesn't constrain it to an enum, send whatever the app's picker uses.

Response 200

{ /* full updated user, same shape as GET /users/me */ }

Errors

  • 400 age / height_cm / weight_kg sent but not numbers
PATCH/users/me/goal User

Set the daily step goal. Must be an integer ≥ 1.

Request

{ "daily_goal_steps": 10000 }

Response 200

{ /* full updated user */ }

Errors

  • 400 missing, non-integer, or < 1
There is no /users/me/goal/recommended endpoint. The “recommended daily steps from height / weight / age” calculation is deliberately client-side — pure arithmetic the app computes on-device. Compute it locally and PATCH the result here.

Steps

All require a bearer token, all act on the logged-in user.

GET/steps/today User

Today's progress against the current goal.

Response 200

{ "goal": 8000, "today": 4200 }

goal is the user's current daily_goal_steps. today is 0 if nothing has been synced yet today.

POST/steps/sync User

Upsert a step count for a date. Safe to call repeatedly for the same entry_date — the latest value for a date always wins, it does not add to the previous value. entry_date must be YYYY-MM-DD; step_count must be an integer ≥ 0.

Request

{
  "entry_date": "2026-08-21",
  "step_count": 4200
}

Response 201

{
  "id": "2451c88d-3c60-41df-aa91-965227340385",
  "user_id": "39d76e58-4557-45e8-8e54-fd6d1535e384",
  "entry_date": "2026-08-21",
  "step_count": 4200,
  "created_at": "2026-08-21T16:12:25.941Z",
  "updated_at": "2026-08-21T16:12:25.941Z"
}

On a repeat sync for the same date, id and created_at stay the same; step_count and updated_at change.

Errors

  • 400 bad date format or negative step_count
GET/steps/history?days=30 User

Raw daily entries, newest first. days (optional, default 30) is a rolling window back from today.

Response 200

[
  { "entry_date": "2026-08-21", "step_count": 4200 },
  { "entry_date": "2026-08-20", "step_count": 6100 }
]

Only dates with a synced entry appear — no zero-filled gaps for missing days.

GET/steps/report?days=7 User

Rolling-window summary. Use days=7 for “this week”, days=30 for “this month”, or any custom window. days defaults to 7.

Response 200

{
  "period_days": 7,
  "days_logged": 5,
  "total_steps": 28400,
  "avg_daily_steps": 5680
}
  • days_logged — how many of the period_days actually have a synced entry, not the window size.
  • avg_daily_steps — total_steps / days_logged, rounded. Averages over days with data, so it isn't dragged down by days with no sync.
  • If nothing was synced in the window, days_logged and total_steps are 0 and avg_daily_steps is 0.

Notifications

Requires a bearer token.

GET/notifications User

The current user's notifications, newest first.

Response 200

[
  {
    "id": "b1f2...",
    "user_id": "39d76e58-4557-45e8-8e54-fd6d1535e384",
    "title": "Goal reached!",
    "body": "You hit 10,000 steps today.",
    "type": "achievement",
    "created_at": "2026-08-21T09:00:00.000Z"
  }
]

type is one of "achievement" | "reminder" | "summary".

Nothing generates notification rows server-side yet — no cron, no push, no automatic “goal reached” trigger. This endpoint returns [] for every user right now. It's wired up and ready, but there is no producer. Don't build UI that assumes a steady stream until that lands — flag it if it blocks a screen. Relative time (“2h ago”) is client-side too; format from the ISO timestamp.

Admin

Requires a bearer token whose user has role: "admin". There is no admin signup — accounts are promoted by hand in the database. A non-admin token gets 403 on every route below. These return cross-user aggregate / list data for an internal dashboard, not anything scoped to the current user.

GET/admin/overview Admin

Top-line platform metrics.

Response 200

{
  "total_users": 1042,
  "new_users_today": 6,
  "new_users_7d": 41,
  "new_users_30d": 210,
  "active_users_7d": 388,
  "active_users_30d": 701,
  "total_steps_logged": 812345000,
  "avg_daily_steps_7d": 6210,
  "goal_completion_rate_7d": 0.34
}
  • “Active” = synced at least one step_entries row in that window.
  • avg_daily_steps_7d averages over logged entries in the last 7 days across all users, not per-user.
  • goal_completion_rate_7d — fraction (0–1) of (user, day) rows in the last 7 days meeting that user's current daily_goal_steps. There's no goal-history table, so a user who recently raised their goal shows past days as “missed” against the new target.
GET/admin/users?page=1&limit=20&search= Admin

Paginated user list, newest-registered first. page (default 1), limit (default 20), search (optional, case-insensitive substring match on full_name or email).

Response 200

{
  "items": [ /* full user objects, same shape as GET /users/me */ ],
  "total": 1042,
  "page": 1,
  "limit": 20
}
GET/admin/users/:id Admin

One user's profile plus their last 30 days of step entries.

Response 200

{
  "id": "...",
  "full_name": "Jane Doe",
  "...": "...same fields as GET /users/me...",
  "step_entries": [
    { "entry_date": "2026-08-21", "step_count": 4200 }
  ]
}

Errors

  • 404 :id doesn't exist
PATCH/admin/users/:id Admin

The only admin write. Enables or disables an account.

Request

{ "is_active": false }

Response 200

{ /* full updated user */ }
Disabling a user does not invalidate their existing token — a token issued before disabling keeps working until it expires (role / is_active aren't re-checked per request, only at login). It does block their next /auth/login with a 403.

Errors

  • 404 :id doesn't exist
GET/admin/stats/signups?days=30 Admin

Signups per day, oldest first. days defaults to 30. One entry per day that had ≥ 1 signup — no zero-filled gaps.

Response 200

[
  { "date": "2026-08-20", "count": 3 },
  { "date": "2026-08-21", "count": 6 }
]
GET/admin/stats/steps?days=30 Admin

Step totals per day, oldest first. days defaults to 30. One entry per day that had ≥ 1 sync — no zero-filled gaps.

Response 200

[
  { "date": "2026-08-20", "total_steps": 812345, "active_users": 140 },
  { "date": "2026-08-21", "total_steps": 903221, "active_users": 152 }
]

total_steps sums step_count across all users for that date. active_users counts distinct users who synced that date.
